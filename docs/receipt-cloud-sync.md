# Receipt cloud sync: implementation foundation (not enabled)

Receipt attachments currently remain local to each device, including PDF receipts. **There is no working cloud receipt sync in the app yet.** The Storage rules and the transport-independent integrity primitives in `receipt-sync/core.cjs` are a foundation only. Do not deploy these rules or change the UI's local-only description until the integration and security validation below are complete.

## Intended behavior and authorization

- Keep original PDFs as PDFs and image receipts as images. Never put attachment bytes in the Firestore snapshot or public-report projection, and do not distribute Firebase download-token URLs. Read individual objects with authenticated SDK calls after checking the active account and workspace.
- Store immutable, UUID-named objects under `organizations/{orgId}/receipts/{id}`. Proposed rules let current members read known objects, restrict create to current owner, disbursing and project-manager members, reject list/update/delete and limit objects to 1 MiB and permitted MIME types. Firestore membership is checked on each Storage request. Reviewers are read-only. Users who already downloaded a file can retain a copy after removal; no cloud rule can revoke that copy.
- The object reference should contain a UUID, SHA-256 digest, MIME type and byte length, never a download URL. Verify file signature, size and digest on upload and download. Object names must not expose contributor or receipt details. Storage rules validate metadata, not actual file bytes or whether a PDF is safe to open; downloaded files should be treated as untrusted.
- Existing local files must not be silently presented as shared. New or historical local-only files should only be marked shared after upload is confirmed and the matching Firestore snapshot is committed. The per-file UI must distinguish local, pending, shared and failed/unavailable states; it must allow retry, and must never report success based on local save alone.

## Remaining integration (blocking)

1. Provision a Firebase Storage bucket, configure authenticated browser access/CORS and assess billing, quota, retention and regional requirements. No bucket or credentials are created by this patch. `firebase.json` intentionally does not enable these Storage rules, to avoid accidentally replacing rules for an existing bucket.
2. Integrate the preliminary `receipt-sync/firebase-transport.cjs` adapter with the Firebase Storage SDK and test create-only upload, authenticated bounded byte reads, exact error handling (only object-not-found is absence), no `getDownloadURL`, and cancellation/stale-account checks. The CJS files here are prototypes and are not yet bundled or wired into the browser app.
3. Persist a durable, per-account/per-organization offline upload queue and immutable receipt references. Do not rely on the current `localStorage` workspace cache: it has a small quota and duplicates the snapshot. Confirm local persistence before queueing or publishing. Upload before committing the reference, keep retryable pending state through reload, and prevent workspace switches/account changes or conflicting snapshot updates from misattributing an upload. Handle interrupted uploads, two-device edits, permission loss, deleted/voided records and orphaned objects without losing history or overwriting another user's file.
4. Provide an explicit, safe migration for existing local attachments. Do not automatically overwrite a different cloud attachment or assume a missing local file is a deletion. Device-local attachments can differ for the same record. Account for attachments copied into audit records and require explicit behavior for removed records.
5. Implement an authenticated download path and clear per-attachment status/actions across refunds, transactions and contributions, including a usable offline cached copy. Do not attach cloud files to in-memory snapshots in a way that bloats Firestore, localStorage, or team drafts.
6. Update JSON export/import and recovery: cloud-only files must either be downloaded into a complete backup with explicit failures, or clearly reported as missing. Keep existing local image/PDF backup support and don't let a partial backup appear complete.
7. Test Storage and Firestore rules together using Firebase emulators: anonymous/nonmember/cross-org requests; every role; removal/role changes; list/delete/overwrite; object size/type/metadata; downloads after removal; invalid refs; and malicious/tampered objects. Run end-to-end tests with two users/devices, offline/restart/retry, conflict, revocation, quota errors, migration, backup/restore and orphan cleanup. Verify that ordinary and audit attachments never enter the shared Firestore document or public reports.
8. Plan trusted orphan cleanup and retention without deleting referenced or pending files, and handle older clients without their stripping or losing references. Coordinate Storage rules, app release and existing organization-discovery migration; back up data first. Enable only after all tests pass and an explicit production rollout decision.

No Firebase resource, rules, backend, or app was deployed by this work.
