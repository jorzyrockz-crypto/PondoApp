# Sample data preview

Settings → Data → **Load sample data** adds fictional, marked examples alongside the active workspace's records. Examples include at least two of each common record-creating form: funds, projects, allocations, income, expenses, donations, supplier payables, refunds, contribution activities and payments (regular, monthly and project fundraising), Death Aid records and payments, signatories, and Other Funds payments. They also include paid and partially paid refunds, an itemized refund, a non-cash refund credit, fictional void history and a fictional Death Aid handover. Names and descriptions are labeled `[Sample]`. A generated receipt labeled SAMPLE is stored only on the device by default. Dates are illustrative, not future-dated; monthly periods use the current and previous month.

Sample entries affect balances, dashboards, reports and backups, and can sync to members of a team workspace. Loading and clearing require confirmation and a writable, confirmed workspace; neither is available to a reviewer or a workspace locked for recovery. A workspace, access or record change during confirmation cancels the operation. Only one full set of samples can be loaded at a time. If an older or partial sample set has fewer than two marked Other Funds payments, **Add Other Funds samples** adds only the missing payments without clearing or changing existing records. Use **View Other Funds** to open the register.

**Clear sample data** removes marked sample records, including edits to those marked records. It never cascades into unmarked records. If an unmarked transaction, payment, allocation, contributor, refund, activity or handover depends on sample data, a sample payment has an unmarked handover, a sample record has a pending request, or a sample refund contains unmarked non-cash credits, clearing is blocked until the dependency is resolved. Clearing is also blocked when the remaining core records would fail financial validation. Back up your records before resolving dependencies. An unmarked historical audit entry is retained. Save failures are reported; follow the storage warning and export the current data before reloading.

An owner can optionally include one real shared editor receipt when online and synced in a disposable team workspace registered as `Pondo Sample Test`, or as `Pondo Sample Test ` followed by a suffix. The exact name is allowed; a suffix can distinguish multiple test workspaces. The editable display name does not qualify a workspace. This opt-in requires typing CREATE and uses the normal atomic snapshot/receipt sync and existing rules; confirm team sync before relying on it. The shared receipt document is immutable under ordinary rules and survives Clear sample data; it is not covered by JSON backup or currently removable through the app. Permanent workspace deletion is not available. Use only a disposable workspace; the name check is an accident guard, not a security boundary.

Sample loading does not create team accounts, invitations, member refund inbox requests, account-confirmed Other Funds handovers, reviewer receipt documents, public reports, Storage objects or historical/orphaned records. Sample Other Funds payments cannot initiate real account-confirmed handovers; use an actual payment and two authenticated workspace accounts to exercise that workflow. Clearing sample Other Funds payments in a team workspace requires a server-confirmed handover view with no linked handover; it is blocked while the view is unavailable or a linked handover exists. It is not a complete Firestore deletion test or a substitute for an administrative inventory. Never use fictional entries as real financial records.

The shared-receipt checkbox explains why it is unavailable. It needs the active registered test workspace, a signed-in and server-confirmed owner, a clean server-confirmed team copy, no existing samples, working local storage and receipt support. A reported connection alone does not establish that the server accepted the receipt.
