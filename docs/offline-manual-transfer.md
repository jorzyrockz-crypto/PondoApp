# Review and copy offline tracker data

The device-only **Continue offline** tracker is separate from signed-in workspaces. It does not automatically sync. To transfer it, sign in on the same browser/device, open the destination (Personal or a team), then open **Settings → Data → Review offline changes**. For a team, wait for online, server-confirmed membership and a clean, confirmed team snapshot; reviewers cannot copy financial records into the team ledger.

The review lists each added record and each same-type/same-ID conflict. Expand a record to see its fields and local images. Choose **current workspace** or **offline** for every conflict; the copy is unavailable until all conflicts are resolved and the resulting supported financial links validate. Confirming copies the selected records without deleting source or destination-only records. A second review skips identical records, making retries safe for the same IDs. Records with different IDs can still be duplicates: inspect carefully. Organization details, settings, deleted records, team request history and external Firestore documents are not transferred. This is a one-way copy, not a two-way or automatic synchronization.

A selected offline record, or destination record selected for replacement, with a shared-receipt reference or pending approval/deletion is blocked: those refer to workspace-specific cloud workflows and cannot safely be recreated by copying a snapshot. Images embedded in ordinary records remain device-local when copied to a team; they are not uploaded as shared receipts. The review handles at most 500 changed/conflicting records, and its validation covers supported schemas and relationships, not the truth or completeness of financial data.

The offline copy is never deleted. The application checks the source and destination again after confirmation and stops if the account, workspace, access, data or team baseline changed. Team copies are first saved locally and queued through the existing revision-checked sync; the success message says to wait for team sync, not that the server has confirmed it. A conflict or failure requires existing team-draft recovery and manual reconciliation; keep the offline data and independent verified backups. Browser storage can fail or be cleared. Tests include synthetic local storage and mocked team UI plus existing Firestore sync tests; real devices, deployment, multiple-user races, quotas and failure recovery need staging verification.
