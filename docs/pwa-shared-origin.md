# PWA sharing an origin

Pondo's manifest keeps its existing `/PondoApp/` identity. Its worker is registered at the app's path and uses `pondo-vN` cache names; activation only removes older caches with that exact naming pattern. The update UI verifies the expected script URL and scope before using a registration and refuses a foreign worker at that scope. The worker also leaves requests for sibling paths alone. These are safeguards against accidental interference, not a security boundary: same-origin scripts can access shared browser storage or deliberately register workers, and checks cannot eliminate races with other same-origin code. Separate origins are required for stronger isolation.

## Portable School Inventory audit

At Portable-School-Inventory main commit `d4e8dfcaa8462eede30419c13ac40d3c2ae26372`, its manifest ID `./` resolves against the **origin**, producing the root ID, rather than its app path. This differs from Pondo's existing ID, but can collide with other root-ID apps. Its worker uses a separate relative scope and `custodianpro-` cache names. Do not silently change the manifest ID of an installed app: changing it may create a separate installation, not migrate the old one. Back up data and test the installation transition first.

More importantly, the inventory app's explicit Reset app action calls `localStorage.clear()`, `sessionStorage.clear()` and attempts to delete every IndexedDB database returned by `indexedDB.databases()`. On a shared origin this can affect Pondo and other apps' locally stored data and sign-in state. It is not an automatic update action. Avoid that reset until the inventory app is changed and tested; do not clear site data as a workaround. Fixing this requires work in that repository: remove only the inventory app's own well-identified keys and databases, taking care not to delete Firebase databases shared with other apps. Preserve existing data and test with both apps installed. Pondo cannot prevent a sibling page from clearing origin-wide storage.
