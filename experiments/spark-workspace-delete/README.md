# Spark workspace cleanup experiment — NOT deployable

This isolated prototype explores a Firestore-only owner freeze and resumable, bounded cleanup. It is **not connected to the app**, is not part of `firebase.json`, and must not be deployed or used on real workspaces. Starting the experiment irreversibly locks a workspace; it intentionally has no finalization or parent-deletion path.

The candidate rules freeze discoverability and ordinary workspace access for members, stop invite redemption and writes, and permit only the initiating owner to enumerate and delete a fixed list of direct collections, including the known Faculty Fund direct collections, and matching invites. Isolated fixtures extend the freeze guard to Faculty test, release-candidate, and recovery-candidate access paths; they are generated from their respective review-only rule sources. When a member or join request is removed, the prototype atomically removes that workspace from their profile membership array and deletes that workspace’s request index, without granting the owner profile read access or permission to alter unrelated fields. Matching active and legacy pointers are cleared as part of the same write; pointers to other workspaces remain unchanged. For other users, the prototype tests bounded write variants against rules without reading private profiles; one member is processed per batch. The initiating owner’s own profile is updated transactionally to avoid overwriting a concurrent selection. The owner membership and parent remain so cleanup can resume. The experimental client clears one server-confirmed batch at a time and, after known groups are empty, reports only `awaiting-verification`, **not** deletion success. Retrying an interrupted batch is safe for the listed paths; account and workspace changes stop further batches. Security is enforced by the candidate rules, not the client checks.

Important blockers before any real use:

- The experiment does not enumerate unknown/nested collections, nested or historical Faculty Fund data, server-only backups, or any previously used variants. An administrator's [read-only inventory](../../docs/workspace-deletion-inventory.md) is needed, but is not by itself a complete external-record audit.
- Indexes of unknown or former members, the retained owner membership/profile, notices, public report copies, Storage files and other external records are not cleaned. Users can still write their own profile indexes while a workspace is locked, so stale personal references can reappear; they do not grant access. Existing offline/downloaded copies cannot be revoked. Server clients bypass rules and must be disabled or coordinated separately.
- Synthetic tests exercise the ordinary, Faculty test, release-candidate and recovery-candidate freeze guards, but do not establish parity with the actually deployed rules or a complete security proof. In particular, Faculty release controls, recovery sessions, restore locks, verified backups and their nested entries remain on disk and are not cleaned by this prototype. It has no recoverable UI, no finalization proof, no fully tested concurrency and quota strategy, no storage cleanup and no safe registered-name reuse. Firestore rules cannot prove that client-side collection cleanup is complete.
- Its tests use synthetic emulator data, never production. Keep the UI disabled and the production rules unchanged. Actual rollout needs completed implementation, explicit data inventory, security review, emulator and staging tests, coordinated rules/client deployment, and a recovery plan.

To regenerate the isolated Faculty fixtures after changing their source rules, run `node experiments/spark-workspace-delete/generate-faculty-candidate.cjs`; use `--check` to detect drift. The emulator workflow tests all four experimental variants with synthetic data.
